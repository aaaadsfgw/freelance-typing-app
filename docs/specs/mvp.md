# Dev Desk — MVP 仕様書

表示名: **Dev Desk**（内部リポジトリ / Worker / D1 名は互換のため既存のまま）  
フェーズ: MVP 実装。最終 UI は **C ベース + A の返信感**

本文中の「暫定」は、仕様が曖昧だった箇所に対する **MVP として最も単純かつ自然な案** である。大きな機能は追加していない。

---

## 1. アプリの目的

今どきの IT 企業で働く Web エンジニアとして、Slack 風チャットに届いたメッセージへ返信していくタイピングゲーム。

プレイヤーは提示された返信文をローマ字で入力し、制限時間内にできるだけ多くの連絡を処理する。メインスコアはゲーム内の **年収** である。

単なる文章タイピングではなく、「フルスタック Web 開発部署でチャット対応している感覚」を楽しめることを目的とする。

---

## 2. ターゲットユーザー

- ローマ字入力で日本語タイピングを練習したい人
- IT・Web 制作に関心がある人、またはその周辺で働く人
- 業務で使いそうな文章（丁寧な返信、IT 用語、英数字、記号）を自然に触れたい人
- タイピング初心者から、長文・記号混じりを鍛えたい中上級者まで（難易度 3 段階）

スマートフォン専用体験は MVP 対象外。デスクトップの Web ブラウザを主対象とする。

---

## 3. コンセプト

**タイピングで伸ばす、今どきの IT 企業 Web エンジニア体験**

タイピング速度だけでなく、次を自然に練習できる内容にする。

- 業務で使いそうな文章
- 丁寧な返信
- IT 用語
- 英数字・記号
- Issue / PR
- Markdown 的な表現

ゲーム中のループは次を重視する。

チャットが届く → 返信する → 年収が上がる → 次のメッセージが来る

テンポを非常に重視する。1 件返信するたびに長い演出やボタン操作を挟まない。

---

## 4. 世界観

主人公は IT 企業勤務の Web エンジニア。Web アプリをフルスタックで開発する部署に所属し、社内メンバー・他部署・顧客・取引先からチャットが届く。会社はなぜかトラブルが多いが、仕事そのものを不快には描かない。

連絡の種類（例）:

- 小規模な Web サイト
- EC サイト
- 社内システム
- Web アプリ
- LP
- 管理画面
- API
- 保守案件

相手には個性を持たせる。ただし特定の人物を不快に描きすぎず、軽いユーモアとして扱う。

例:

- 丁寧な企業担当者
- 技術に詳しくない顧客
- 急ぎの依頼が多い顧客
- 細かい修正を何度も頼む顧客
- 技術に詳しいスタートアップ担当者
- なぜか毎回金曜夕方に連絡してくる顧客

ゲーム全体のテイストは、仕事をネガティブに描くのではなく、**忙しいけれど少し楽しい社内チャット生活** とする。

主人公の特徴:

- 基本的に丁寧で、仕事のできるエンジニア
- カタカナ語が好きで、使うほど格好いいと思っている
- 1 返信につき軽い冗談やボケを 1 つ入れる
- 技術的な内容にも対応できる
- 顧客・社内どちらにも比較的柔らかく接する
- 難易度が上がるほど自信が増す（新米 → 調子に乗る → つよつよ）

冗談は短く、タイピングの邪魔にならない範囲にする。文章としての自然さを最優先する。

## 5. MVP の範囲

MVP で実現する範囲は次のとおり。

- タイトル画面からの難易度選択とゲーム開始
- 制限時間内の連続案件処理（1 件ずつ）
- ローマ字入力による日本語返信
- ゲーム内年収を主スコアとした結果表示
- 入力速度・正確性・ミス・コンボ・返信完了数の表示
- プレイごとのタイピング分析（苦手キー / 指 / キー遷移）
- デスクトップ Web 上でのプレイ

UI の見た目は、採用した UI 案をベースにする（本フェーズでは未確定）。

## 7. ゲームルール

### 7.1 1 セッションの意味

1 回のプレイは、ゲーム内の **1 ヶ月分の仕事** として扱う。セッション終了時の累計が「ゲーム内年収」になる。

### 7.2 制限時間（暫定）

全難易度共通で **90 秒**。

難易度の差は時間ではなく、文章の長さ・語彙・記号量・報酬の出方で出す。

### 7.3 案件の進行（暫定）

- 同時に扱う案件は **1 件だけ**
- 正しく全文入力すると返信完了
- 年収 UP が加算される
- **操作なしで** 次のメッセージが届く
- 制限時間が 0 になると入力を打ち切り、結果画面へ進む

### 7.4 開始から終了

1. タイトル画面を開く
2. 難易度を選択してゲーム開始
3. 社内または取引先からメッセージが届く
4. 入力する返信文が表示される
5. プレイヤーがローマ字でタイピングする
6. 正しく全文入力すると返信完了
7. 短時間のフィードバックのあと、次の依頼が届く
8. 制限時間終了まで繰り返す
9. 結果画面でゲーム内年収と成績を確認する
10. 再挑戦、難易度変更（タイトルへ）、またはタイピング分析へ進む

---

## 8. 難易度

3 段階。プレイヤーがタイトル画面で選ぶ。

### 8.1 初級: 新米エンジニア

- 短い文章、1〜2 文程度
- 日本語中心、英数字・記号は少なめ
- 単純な確認や報告、丁寧な返信が中心
- 社会人として初々しい。ボケは控えめ
- タイピング初心者でも遊びやすい

例:

相手: 修正内容を確認してもらえますか？  
返信: 確認します。少々お待ちください。バグには少し席を外してもらいます。

### 8.2 中級: 慣れてきたエンジニア

- 2〜3 文程度
- 技術用語、英数字、Issue / PR 番号、@ メンション、Markdown 的表現が増える
- 仕事に慣れて、ちょっと調子に乗り始める

例:

相手: PR #128 の修正内容を確認してもらえますか？  
返信: 確認します。API 周りを中心にレビューします。問題なければ本日中に反映します。このくらいならコーヒーが冷める前に終わります。

### 8.3 上級: つよつよエンジニア

- 長めの返信、複数行
- 英数字・記号、Issue / PR、Markdown、技術用語が多い
- 状況説明や複数作業のまとめ、緊急案件も登場する
- **難しいのは技術知識ではなく、タイピングとして難しい文章**
- 専門知識がないと意味が分からない状態にはしない

## 9. スコア

### 9.1 メインスコア

ゲーム内の **年収**。返信 1 件完了ごとに年収 UP を加算する。内部の `revenue` カラムは互換のため残す。

表示の例:

- 返信完了: 年収 UP +¥420,000
- ゲーム中: ゲーム内年収 ¥4,280,000
- ゲーム終了: ゲーム内年収 ¥6,840,000

### 9.2 報酬の決まり方（UX のみ。計算式は未確定）

報酬は次を反映する。

- 入力速度
- 正確性
- ミス数
- 難易度
- 文章量

画面上では **速く正確に仕事を処理するほど稼げる** ことが分かればよい。具体的な計算式はこの段階では決めない。

### 9.3 サブスコア

ゲーム中または結果画面で扱う。

- 入力速度
- 正確性
- ミス数
- 最大連続入力数（コンボ）
- 返信完了数

可能であれば結果画面に次も出す（MVP で含める。算出は単純でよい）。

- 平均年収 UP 額
- エンジニア称号（速度・正確性・対応数。年収額では決めない）
- 一言評価

## 10. タイピングルール

### 10.1 表示と入力

- 画面上には自然な日本語文章を表示する
- プレイヤーはローマ字入力で文章を完成させる
- ユーザー自身が返信内容を考える必要はない。入力する返信文はあらかじめ提示する

### 10.2 正誤（暫定）

- 正しいキーを押すとその文字（またはローマ字 1 打）が進む
- 誤入力ではカーソルは進まない
- ミスとしてカウントし、コンボをリセットする
- Backspace による訂正操作は MVP では不要とする（進まないため）

### 10.3 ローマ字の揺れ（暫定）

一般的な日本語ローマ字の複数表記は許容する方針とする。

例: 「し」は `si` / `shi`、「つ」は `tu` / `tsu`

どの表記表を使うかは実装時に決める。仕様としては「一般的な入力方法で通る」ことを優先する。

### 10.4 コンボ（暫定）

連続して正解したキー数。ミスで 0 に戻る。ゲーム中に現在値、結果画面に最大値を出す。

### 10.5 ローマ字ガイド（確定）

ゲーム画面にローマ字ガイドを置く。**ON / OFF で切り替え** できる。初期値は ON（暫定）。

OFF のときは日本語の返信文と、入力済み / 現在文字 / 未入力の区別だけを出す。

## 11. 問題文章のルール

### 11.1 題材

実際の IT 企業の Web 開発部署にありそうな連絡を題材にする。社内（PM / デザイナー / QA / 営業 / インフラ / バックエンド / フロント / 上長 / 同僚）と、顧客・取引先を混ぜる。

例: Web サイト修正、UI 修正、バグ報告、動作確認、仕様確認、追加機能の相談、納期確認、進捗報告、顧客への説明、修正完了報告、リリース確認、GitHub の PR / Issue、デザイン変更、API / DB 関連の確認、エラー報告、緊急対応、ミーティングの日程調整、見積もりや作業内容の確認

IT 技術だけに偏らず、**社内外とのコミュニケーションも必要になる文章** を含める。カタカナ語は自然な範囲で少し多めにする。

### 11.2 混ぜてよい要素

問題文には次を自然に混ぜる。

- `PR #128` / `Issue #42`
- `API` / `DB` / `UI`
- `main` / `develop`
- `404` / `500` / `v1.2`
- `@tanaka`
- `TODO`
- Markdown 的な記号

### 11.3 避けるもの

- 長い URL
- 長いハッシュ値
- 長すぎるファイルパス
- 意味のないランダム文字列
- 入力負荷だけが高い内容
- AI 特有の不自然に丁寧すぎる文章
- 毎回同じ決まり文句ばかりの文章

問題文は、**実際の仕事で送っても違和感の少ない日本語** にする。

## 13. 各画面の目的

### A. タイトル / スタート

ゲームの世界観を伝え、難易度を選んで開始する。分析画面への入口も置く。

### B. ゲーム

案件を連続処理する。タイピング対象の視認性を最優先する。

### C. 返信完了フィードバック

報酬と直後の成績を一瞬見せ、テンポを止めずに次の案件へ進める。

### D. 結果

ゲーム内年収と成績を楽しんで確認し、再挑戦・難易度変更・分析へ進む。

### E. タイピング分析

苦手なキー・指・キー遷移を確認する。練習の振り返り用。

## 14. 各画面の主要 UI

### A. タイトル / スタート

- ゲームタイトル
- コンセプト説明
- 難易度選択（初級 / 中級 / 上級）
- ゲーム開始
- タイピング分析への導線

### B. ゲーム

最低限表示する。

- 相手の名前
- 相手のアイコン
- プロジェクト名
- 届いたメッセージ
- 入力対象となる返信文
- 現在入力済みの部分
- これから入力する部分
- ミスタイプ
- 残り時間
- 現在のゲーム内年収
- 連続入力数（コンボ）
- 返信完了数
- ワークスペース名とチャンネル名（Slack 風。巨大サイドバーは置かない）

特に **今どの文字を入力すべきか** が瞬時に分かるようにする。装飾よりタイピングの視認性を優先する。

採用レイアウト（C ベース + A の返信感）:

- ゲーム内年収・残り時間・コンボを、画面上部の HUD で大きく目立たせる（C）
- タイピング対象の返信文は **画面中央に 1 箇所だけ**、最も大きく置く（C）
- 相手の名前・アイコン・プロジェクト名を、入力文の上で常に識別できるようにする（A）
- 届いたメッセージは、チャット風の吹き出しで 1 回だけ表示する（A）
- タイピング領域は「返信中」と分かるラベルと配置にする（A）
- 入力対象を吹き出しと入力欄の両方に出さない。視線移動を増やす重複は禁止する
- 返信完了時の報酬・正確性・コンボは、入力領域の直下に短時間表示する

### C. 返信完了フィードバック

短時間表示する。

- 年収 UP
- 入力速度
- 正確性
- コンボ

独立した確認ボタンは置かない。

### D. 結果

- ゲーム内年収
- 入力速度
- 正確性
- ミス数
- 最大連続入力数
- 返信完了数
- 平均年収 UP 額
- エンジニア称号
- 一言評価
- 再挑戦
- 難易度変更（タイトルへ戻る）
- タイピング分析への導線

### E. タイピング分析

- 苦手キー（入力回数 / ミス回数 / ミス率）
- 苦手な指
- 苦手なキー遷移（連続 2 キー程度）
- 全体的な入力成績

## 15. 基本ユーザーフロー

```
タイトル
  ├─ 難易度選択 → ゲーム開始 → 案件ループ → 時間切れ → 結果
  │                                      ├─ 再挑戦（同じ難易度でゲームへ）
  │                                      ├─ 難易度変更（タイトルへ）
  │                                      └─ タイピング分析
  └─ タイピング分析 → タイトルへ戻る
```

案件ループ:

```
依頼表示 → タイピング → 全文正解 → 短い報酬フィードバック → 次の依頼
```

## 16. タイピング分析

各プレイ時に取得・格納し、専用画面から確認する。高度な AI 分析は不要。

### 16.1 苦手キー

キーごとに入力回数・ミス回数・ミス率を出す。

### 16.2 苦手な指

一般的なタッチタイピングでの物理キーと指の対応から集計する。

- 左小指 / 左薬指 / 左中指 / 左人差し指
- 右人差し指 / 右中指 / 右薬指 / 右小指

親指（スペース）は MVP では集計対象外とする（暫定）。

### 16.3 苦手な動き

連続する 2 キー程度のキー遷移を対象とする。例: `tr` / `ou` / `pr` / `io`

プレイヤーが「どのキー」「どの指」「どのキーの組み合わせ」でミスしやすいかが分かればよい。

格納の技術方式は決めない。仕様上は **直近のプレイと、これまでの累計** を分析画面で見られれば十分とする（暫定）。

## 18. UI/UX の優先順位

次の順番で重視する。見た目を優先してタイピングしづらくしない。

1. タイピング対象が読みやすい
2. 現在入力すべき文字が分かりやすい
3. ミスタイプがすぐ分かる
4. 残り時間が分かる
5. 年収が増える楽しさがある
6. チャットで会話している感覚がある
7. 社内の Web エンジニアとして働いている感覚がある
8. 世界観
9. 装飾

基本方針:

- 現代的な Web サービスらしい
- 今どきの IT 企業の業務チャット感
- 白をベースに、ビビッドカラーをアクセントにする
- カラフル、ポップ、少しゲームらしい
- Slack そのもののコピーはしない
- 「Dev Desk」という架空の社内チャット UI

### 18.1 最終 UI（確定）

**ベースは案 C（ゲーム性重視型）**。参照モックは `ui-proposals/game-c.html`。

C から維持する:

- タイピング対象が中央で最も大きい
- ゲーム内年収・残り時間・コンボが一目で分かる
- ローマ字ガイドは **ON / OFF 切り替え**（初期値は ON。暫定）
- タイトル / 結果 / 分析も、大きな数字と短い HUD のトーンに揃える

A から取り入れる（ゲーム画面のみ）:

- 相手の名前・アイコン・プロジェクト名が分かる
- 依頼文をチャット風の吹き出しで表示する
- タイピング領域が「返信している」と自然に分かる

取り入れない:

- A の「入力対象を複数箇所に出す」構成
- 案 B の管理画面レイアウト（サイドバー、KPI カード群、案件キュー）

優先順位は変わらない。返信感のために、入力文の大きさや HUD の見やすさを下げない。

## 19. 将来的な拡張候補

MVP では実装しない。アイデアとして残す。

- オンラインランキング
- ユーザーアカウントと成績のクラウド保存
- 日次 / 週次チャレンジ
- 相手やカテゴリの解放
- もう少し長いストーリーや季節イベント
- 練習モード（苦手キーに絞った短文）

## 20. 実装メモ（MVP）

仕様を大きく変えず、実装時にだけ決めた値。

- 制限時間: 90 秒
- ローマ字ガイド初期値: ON
- 表示名: Dev Desk
- 年収 UP: 難易度の基礎額 × 文章量係数 × 速度係数 × 正確性係数。10,000 円単位に丸める。下限 ¥200,000
  - 基礎額: 初級 ¥400,000 / 中級 ¥650,000 / 上級 ¥950,000
- 各返信の末尾に、難易度別 persona line を question id から 1 つ決定して付ける
- 問題は D1 から取得する。返信文は表示用テキストと、文字ごとの読み（チャンク）を持つ
- プレイ中のキー記録はブラウザ内。終了時に 1 回だけ保存する
- 匿名 ID は localStorage。ログインなし
